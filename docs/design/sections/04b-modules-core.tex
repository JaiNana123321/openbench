\field{Purpose}
Allocation decides, one Request Line at a time, whether the capacity it asks for can be had now, and records the answer as rows; a Hold is simply the state \code{HELD} of such a row. Everything that differs between Allocation Classes lives here, behind one interface that \module{Requests} drives without branching on the class.

\field{Responsibilities}
\begin{itemize}
\item One interface for every Allocation Class (\req{CO-plugin}, \req{QA-extensible}); every allocation decision serialized per Resource Type in the database (\req{QA-correct}).
\item Exclusive lines: conflicts, instance choice, waitlist, and Bump mechanics (\req{Exclusive.Conflict}, \req{Exclusive.Waitlist.Join}, \req{Exclusive.Priority.Bump}, \req{Exclusive.Bump.Effect}). Metered lines: the hourly fit (\req{Metered.Line.Form}, \req{Metered.Pool.Check}), the tier Bump (\req{Metered.Tier.Bump}), and recorded usage (\req{Metered.Usage.Record}). Holds as a row state that blocks like an allocation (\req{Lifecycle.Hold.Place}).
\item Matched lines: Shortlists, approvals, and Loans (\req{Matched.Shortlist.Build}, \req{PE-shortlist}, \req{Matched.Approve.Route}, \req{Matched.Loan.Form}).
\item The holder view of a Resource and Inventory's reduction guard (\req{Inventory.View.Holder}); a type's peak fill for the demand surcharge (\req{Ledger.Surcharge}).
\end{itemize}

\field{Provided interface}
\begin{lstlisting}[language=Java]
interface Allocator {
  AllocationClass allocationClass();
  Evaluation evaluate(LineSnapshot line);                    // SATISFIABLE | NEEDS_APPROVAL | UNSATISFIABLE(reason)
  void hold(LineSnapshot line);                              // Exclusive, Metered: rows in state HELD; Matched: no-op
  void commit(LineSnapshot line);                            // HELD -> ALLOCATED; Matched: form Loans
  Released release(LineSnapshot line, ReleasePart part);     // whole or part; returns the pieces given back; Matched: refused
  void cancel(LineSnapshot line);                            // drop Holds, approvals, waitlist entries; Matched: retire Candidates
}
interface Waitlistable { void join(LineSnapshot line); void leave(LineSnapshot line);
  List<WaitingLine> waitingFor(ResourceTypeId type, TimeWindow freed); }
interface Bumpable { Optional<BumpPlan> planBump(LineSnapshot line); void applyBump(BumpPlan plan); }  // Exclusive (Priority), Metered (tiers)
interface ApprovalDriven {
  Shortlist buildShortlist(LineSnapshot line);               // eligible = skills, available, no overlapping Loan, other Team, active; order by person-days lent this Period, then name
  void select(LineSnapshot line, List<MemberId> candidates, boolean escalated);  // exactly the line's quantity; one approval per Candidate
  boolean candidatesLeft(LineSnapshot line);                 // an eligible Member not yet refused remains
  Approval decide(LineSnapshot line, ApprovalId id, Decision d, String reason, Actor actor, boolean windowLapsed);  // lending Manager or PLANNER (escalated)
  List<Approval> refuseIneligible(LineSnapshot line, String reason);  // the system refuses Approved Candidates no longer eligible (allocate, step a)
  List<Approval> outstanding(RequestId request); List<Approval> escalate(RequestId request);  // escalate returns those escalated
}
class LoanService { Loan endEarly(LoanId loan, LocalDate newEnd); List<Loan> loansOf(MemberId member); }  // served by MatchedAllocator
class HolderService { List<Holding> holders(ResourceId r, TimeWindow w); Page<Resource> free(ResourceFilter f, TimeWindow w); }  // Exclusive only
class UsageService {                                         // Stretch; RESOURCE_OWNER of an in-service Resource of the type
  List<MeteredUsage> usage(PeriodId period);                 // (read-only) ALLOCATED Metered rows overlapping the Period
  MeteredUsage recordUsage(MeteredAllocationId id, int usedUnits);  // once the Period has ended; may be recorded again
}
interface AllocatorRegistry { Allocator forClass(AllocationClass c); <T> Optional<T> capability(AllocationClass c, Class<T> cap); }
interface AllocationLock { void lockTypes(SortedSet<ResourceTypeId> types); }   // SELECT ... FOR UPDATE on resource_type, ascending id
interface AllocationQueries {                                // read-only
  List<Holding> holders(ResourceId resource, TimeWindow window);   // free / HELD / ALLOCATED segments with Team and Request
  List<Loan> loansOf(MemberId member); Optional<Integer> waitlistPosition(RequestLineId line);
  List<Loan> loansFor(RequestLineId line);                   // the Loans a Matched line's commit formed (for postEarning)
  int peakUnitsInUse(ResourceTypeId type, Optional<ResourceId> instance, Instant from);  // backs ReductionGuard
  List<Approval> approvalsAwaiting(MemberId approver);       // outstanding approvals addressed to this Manager; every escalated one for a PLANNER
  List<Approval> escalatedOutstanding(); List<Approval> decidedOnEscalation(MemberId approver);  // the Planners' list; a Manager's decided-for-them list
  List<WaitingLine> waitingStartedBy(Instant now);           // waiting lines whose window has started, for expireWaitingLines
  Released previewRelease(LineSnapshot line, ReleasePart part);  // what release would give back, writing nothing
  List<AllocatedPart> allocatedParts(RequestLineId line);    // what the line holds now
  BigDecimal peakFill(ResourceTypeId type, List<TimeWindow> occurrences);  // Stretch surcharge: largest live share of capacity in any hour, 0 to 1
}
\end{lstlisting}
\code{LineSnapshot} is an immutable copy of a line built by \module{Requests} (ids, type and class, quantity or units, window and recurrence, named Resource or Person, skills, Required and Priority marks, the tier premium locked at submission, submission time, a \code{bumped} flag); \code{ReleasePart} is the whole line, some occurrences, an earlier end, or fewer units. \code{Released} lists the pieces given back (occurrence, window, units) so that \module{Requests} prices the Refund from them. A Loan is not part of a line, so an early end goes through \code{LoanService.endEarly}, which \code{MatchedAllocator} serves, and \code{MatchedAllocator.release} refuses.
% NOTE: the brief names LineSnapshot and ReleasePart without fields; these are the minimum the operations need.

\textbf{Why five operations.} \module{Requests} runs one lifecycle for every line: decide (\code{evaluate}), block capacity while approvals are outstanding (\code{hold}), make it final (\code{commit}), give part back (\code{release}), abandon it before allocation (\code{cancel}). Every class needs exactly these, so they form \code{Allocator}; anything only some classes do sits on a capability, so no class carries empty methods. \code{ExclusiveAllocator} and \code{MeteredAllocator} implement \code{Waitlistable} and \code{Bumpable}, and \code{MatchedAllocator} \code{ApprovalDriven}. The one exception is the no-op \code{hold} of a Matched line, cheaper than a capability check at the one call site that holds every satisfiable line.

\textbf{Registry and extension.} \code{AllocatorRegistry} receives \code{List<Allocator>}, which Spring fills with every \code{Allocator} bean, and indexes it by \code{allocationClass()}; start-up fails if a class has two allocators or none. \code{capability(c, cap)} returns the allocator cast to \code{cap} if it implements it, so \module{Requests} never names a class for waiting (a \code{Waitlistable} class), Bumps (a \code{Bumpable} one), or a Quote (whenever the type has pricing settings; a type without them is booked free, with no Charge). The marks a line may carry follow the class, as the \code{request\_line} checks do: the Priority mark only on an Exclusive line, a service tier only on a Metered line, and a weekly recurrence only on an Exclusive line. A fourth Allocation Class is one new \code{@Component} implementing \code{Allocator} and its capabilities, plus one \code{AllocationClass} constant; \module{Requests}, \module{Ledger}, and the existing allocators do not change (\req{CO-plugin}, \req{QA-extensible}).

\field{Required interfaces}
\module{Inventory}: \code{InventoryQueries.type}, \code{instancesOf}, \code{poolCapacity}, \code{search}, \code{resource}, \code{typesOwnedBy}. \module{Members}: \code{MemberService.availableWithSkills}, \code{isAvailable}, \code{summary} (name, Team, active, roles; the unscoped read for this module's rules), \code{managerOf} (the approver for a Candidate's Team), \code{withRole(PLANNER)} (escalation notices to every Capacity Planner). \module{Settings}: \code{SettingsService.current} (Period, bump cutoffs, Quotas, Day Rate), \code{periods} (usage recording). \module{Notifications}: \code{Notifier.notify} (approval requests, Candidate selected, escalation).

\field{Data owned}
{\raggedright\code{exclusive\_occurrence(id, line\_id, team\_id, request\_id, resource\_id, starts\_at, ends\_at, state, priority, submitted\_at)}, one row per occurrence and instance, and \code{metered\_allocation(id, line\_id, team\_id, request\_id, type\_id, units, starts\_at, ends\_at, state, tier\_premium, submitted\_at, used\_units, usage\_recorded\_at, usage\_recorded\_by)}, a Metered line's live window and units, in states \code{HELD}, \code{ALLOCATED}, \code{RELEASED}, \code{BUMPED}, and \code{EXPIRED} (Hold dropped). The Priority mark, tier premium, and submission time are copied onto the rows so the Bump plan reads only this module's tables; \code{used\_units} lies between 0 and \code{units} and is set with who recorded it and when, or not at all. \code{waitlist\_entry(id, line\_id, type\_id, starts\_at, ends\_at, priority, bumped, joined\_at)}; \code{candidate(id, line\_id, request\_id, team\_id, member\_id, position, starts\_on, ends\_on, retired)}, the days copied for the overlapping-selection rule, unique on \code{(line\_id, member\_id)} among unretired rows; \code{approval(id, candidate\_id, approver\_member\_id, state, decided\_by, decided\_at, reason, escalated)}, in state \code{OUTSTANDING}, \code{APPROVED}, \code{REFUSED}, or \code{CANCELED} (which keeps an earlier \code{decided\_at}), where \code{escalated} is a flag, not a state, that \code{escalate} sets on an Outstanding approval and that stays set after the decision; \code{loan(id, line\_id, member\_id, lending\_team\_id, borrowing\_team\_id, starts\_on, ends\_on, days\_lent, ended\_early)}. \field{Invariants}
\begin{itemize}
\item No two live (\code{HELD} or \code{ALLOCATED}) occurrences on one Exclusive instance overlap; in no hour do a Metered type's live units exceed its Pool Capacity, or a Team's its Quota (\req{QA-correct}).
\item Every write that consumes capacity, and every capacity reduction, comes after the lock on that Resource Type in the same transaction.
\item A line's live rows are all or nothing: every occurrence on the same instances, or the full units for the full window.
\item A line is Bumped only by a line of strictly higher rank (Priority over standard; a higher tier premium over a lower one, a line with no tier lowest) and never by a line of its own Request, and no line is Bumped inside the bump cutoff. A Metered type without a cutoff never Bumps.
\item A Person is in at most one Loan on any day. A Candidate is active and outside the requesting Team, and until escalation only the Manager of the Candidate's Team decides.
\end{itemize}

\field{Failure behavior}
A misfit is a result of \code{evaluate}, never an exception; the codes of Table~\ref{tab:allocation-ops} report bad input or a precondition the caller should have established. Allocator beans use \code{Propagation.MANDATORY}: they never commit alone, and any exception rolls back the whole transition. A 23P01 from either exclusion constraint means a path skipped the lock or a check; the transition rolls back, so nothing is written, and the error is logged as a bug and answered 409 \code{ALLOCATION\_CONFLICT}. The guard in \code{MatchedAllocator.commit} throws the same code. A lock wait past \code{lock\_timeout} (5\,s) or a deadlock is retried once, then reported as \code{ConcurrencyRetryException} (503).

\field{Information hiding}
Row layout, Holds as a state, the constraints, the hourly query, the Bump search, and the Shortlist ranking are hidden behind evaluations and DTOs; hour buckets could replace the computed sum without touching \module{Requests}.

\subsubsection*{Shared parts}
{\sloppy\code{AllocationLock} runs one \code{SELECT ... FOR UPDATE} on \code{resource\_type} per id, ascending (\code{@Lock(PESSIMISTIC\_WRITE)}), at the default READ COMMITTED isolation; a transition calls it once, first, for the types of its own lines, and keeps the locks to commit, so allocation on a type is serial; only a waitlist fill may lock further types later, those of a waiting Request, possibly after an account lock, a case the retry covers (Section~\ref{sec:runtime}). \code{AllocationQueries} reads live rows: \code{holders} cuts a window into free, held, and allocated segments; \code{peakUnitsInUse} is the largest hourly sum of live units, Holds counted, from an instant on; \code{peakFill} is, over the hours of a line's occurrences, the largest share of the type's capacity live (Metered: units over Pool Capacity; Exclusive: in-service instances with a live occurrence over all of them), 0 for a capacity of 0. \code{HolderService} serves the holder view of an Exclusive Resource only (\code{CLASS\_MISMATCH} otherwise) over a window of at most 31 days, hiding the holding Team and Request from a caller outside the scope of Section~\ref{sec:cross}; its free search calls \code{InventoryQueries.search}, then one query for the live rows among the matches.\par} The \code{ReductionGuard} implementation locks the type, computes the capacity after the change, and, if \code{peakUnitsInUse} exceeds it, names the earliest failing hour with the hourly query; the lock lasts until Inventory commits, so nothing slips in between.

\textbf{Pure parts}, unit-tested without Spring or a database: \code{Windows} (half-open overlap; Monday-to-Friday day counts) and \code{common.WeeklyRecurrence} (2 to 52 weekly occurrences expanded in the firm's time zone, so 14:00 stays 14:00 across a daylight-saving change; in \code{common} because \module{Requests} also expands them for Quotes and Refunds), \code{HourlyLoad} (the earliest hour in which per-hour sums plus requested units exceed a limit), \code{ShortlistRanking} (eligibility filter and order), and the Bump searches \code{BumpSearch} and \code{TierBumpSearch}.

\subsubsection*{ExclusiveAllocator}
\textbf{Free instances.} The window and weekly recurrence expand into occurrences; an instance is free when no live row on it overlaps any of them. Without a named Resource the allocator takes the free instances with the fewest \code{ALLOCATED} hours in the Period, ties by id, and every occurrence lands on the same instance. \code{hold} inserts one \code{HELD} row per occurrence and instance, \code{commit} turns them \code{ALLOCATED}, and \code{release} marks given-back occurrences (or a shortened tail) \code{RELEASED}, so history stays. Instances are chosen under the type lock, so the exclusion constraint never fires in normal operation; it stops a double allocation by a forgotten path.

\textbf{Bump plan.} For a Priority line with no free instance, \code{planBump} collects per instance the lines whose live rows overlap its occurrences. An instance can be cleared when all are standard lines of other Requests and none has an occurrence starting before now plus the bump cutoff (a type without a cutoff counts 0). For a quantity above 1 the plan takes free instances first, then cleared instances one at a time, those needing the fewest Bumps first; among instances needing the same number, the one whose earliest-submitted blocker was submitted latest. A line is Bumped whole, being atomic. With no plan the Priority line waits ahead of standard lines. \code{applyBump} marks the Bumped lines' live rows \code{BUMPED} with a bulk JPQL update (or an update plus \code{EntityManager.flush()}) and only then inserts the Priority occurrences as \code{HELD}: Hibernate runs inserts before updates, so without the flush the insert would meet the NOT DEFERRABLE constraint while the old rows are still live. \module{Requests} then joins each Bumped line to its waitlist with \code{bumped} set (scenario S5).

\textbf{Waitlist.} One \code{waitlist\_entry} per waiting Required line. \code{waitingFor} returns the type's entries overlapping the freed window ordered by \code{bumped}, then Priority, then \code{joined\_at}, then id; \code{joined\_at} holds the Request's submission time, not the moment of joining. A line's waitlist position is one more than the entries ahead of it: those of the same type whose windows overlap its own and that come earlier in that order. \module{Requests} takes a line whose start has passed off the waitlist with \code{waitingStartedBy(now)} and \code{leave}, one transaction per line; the Request stays Waiting.
% NOTE: brief 7 names the column joined_at but the SRS orders by submission time; we store the submission time there.

\field{Worked example}
A lab-room type has two rooms and a 24-hour cutoff. On Monday at 10:00 a Priority line asks for Thursday 14:00 to 17:00. Room~1 is blocked by two standard lines, L1 (13:00 to 15:00, submitted September 28) and L2 (15:00 to 18:00, October 1); Room~2 by one, L3 (09:00 to 16:00, September 30). Room~2 needs fewer Bumps, so the plan Bumps L3. Had L3 had another occurrence on Tuesday at 09:00, inside the cutoff, the plan would Bump L1 and L2 on Room~1; had L1 also been a Priority line, there would be no plan and the line would wait.

\subsubsection*{MeteredAllocator}
A line asks for units held concurrently over its whole window, one \code{metered\_allocation} row. Under the type lock, \code{evaluate} runs the query below and \code{HourlyLoad} finds the earliest hour where \code{used} plus the line's units exceed \code{poolCapacity(type)} (\code{POOL\_FULL}) or, when the Team has a Quota on the type, where \code{team\_used} plus the units exceed it (\code{QUOTA\_EXCEEDED}). The pool is checked over the whole window first, then the Quota. The line fits with full units in every hour or not at all. Holds, \code{release} (fewer units or an earlier end), and the waitlist follow the Exclusive rules.

\textbf{Tier Bump} (Stretch, \req{Metered.Tier.Bump}). For a line with a tier that does not fit, on a type with a bump cutoff, \code{planBump} picks lines of other Requests with a strictly lower tier premium (no tier lowest) and live rows overlapping the window, none starting before now plus the cutoff, until every hour fits the Pool Capacity. The pick is greedy, not proven minimal: while an hour is over, the next line with units in such an hour, lowest tier first, then the latest-submitted; then it drops, latest pick first, every Bump the others make unnecessary. A Bumped line loses every live row, a Metered line being all or nothing. If the line would still exceed its own Team's Quota, there is no plan. \code{applyBump} plans again and requires the same plan, marks the rows \code{BUMPED}, flushes, and inserts the line's row as \code{HELD}.
\begin{lstlisting}[language=SQL]
SELECT h.hour, coalesce(sum(m.units), 0) AS used,
       coalesce(sum(m.units) FILTER (WHERE m.team_id = :team_id), 0) AS team_used
FROM generate_series(:start, :end - interval '1 hour', interval '1 hour') AS h(hour)
LEFT JOIN metered_allocation m ON m.type_id = :type AND m.state IN ('HELD', 'ALLOCATED')
  AND tstzrange(m.starts_at, m.ends_at, '[)') && tstzrange(h.hour, h.hour + interval '1 hour', '[)')
GROUP BY h.hour ORDER BY h.hour;
\end{lstlisting}
\textbf{Isolation.} This is correct only at READ COMMITTED, where each statement sees what was committed before it began, so the query, run after the lock, sees all the previous lock holder wrote. REPEATABLE READ takes its snapshot at the first statement, the lock itself, so a waiting transaction would sum stale rows and pass; a local two-session test oversold a pool of 8 to 10 that way. The path never raises the isolation level.

\field{Worked example}
A pool of 8 units holds A (3 units, 10:00 to 15:00) and B (4 units, 13:00 to 17:00); a line asks for 2 units from 14:00 to 17:00. The hourly sums are 7 at 14:00 and 4 at 15:00 and 16:00, so with the line they are 9, 6, and 6: \code{POOL\_FULL} at 14:00, one unit short, and a Required line waits until A gives back that hour. Had the Team owned B under a Quota of 5, 14:00 would also fail the Quota ($4 + 2 > 5$); the pool is checked first.

\subsubsection*{MatchedAllocator}
\textbf{Shortlist.} A Candidate holds every listed skill, is available on every day of the window, has no Loan overlapping any day of it, belongs to another Team, and is active. \code{buildShortlist} takes \code{availableWithSkills(skills, window, requestingTeam)} from \module{Members}, drops Members with an overlapping Loan, and orders the rest by person-days lent in the current Period (weekdays of formed Loans inside it), then name: two indexed queries and a sort of at most 500 Members (\req{PE-shortlist}), redone on every call so profile changes show at once. A named Person is checked only for availability and an overlapping Loan (\code{OWN\_TEAM} for the requesting Team's own Member), and naming counts as the Manager's selection.

\textbf{Approvals.} A Person selected, with an approval Outstanding or Approved, on another line of the same Request whose days overlap is not eligible for this line. \code{select} writes a \code{candidate} row (with its Shortlist position and the line's days) and an \code{approval} for the Manager of the Candidate's Team, and notifies that Manager (requesting Team, window, Earning) and the Candidate. \code{decide} accepts that Manager until the window ends and a Capacity Planner after it; a late lending Manager gets \code{WINDOW\_LAPSED}. An approval re-checks eligibility, because a Loan from another Request may have formed since selection, and fails with \code{NOT\_A\_CANDIDATE}.

\textbf{Loans.} A Person can be approved on two Requests with overlapping windows before either Loan forms. \module{Requests} therefore re-evaluates the line under the type lock at the start of \code{allocate}, before any commit, where \code{evaluate} reports an Approved Candidate who is no longer available every day, or now has an overlapping Loan, as \code{UNSATISFIABLE(NOT\_A\_CANDIDATE)}: a Required line is then unsatisfied and the Request goes to Waiting with a replacement asked; an Optional line is Dropped. \code{commit} repeats the check immediately before forming each Loan only as a guard: a failure there means a path skipped the re-evaluation, so it throws \code{RuleViolation("ALLOCATION\_CONFLICT")} and the transition rolls back. The \code{loan} constraint stops even a path that forgets both. A Loan covers the window's dates with \code{days\_lent} its Monday-to-Friday days. \code{endLoanEarly} calls \code{LoanService.endEarly}, which sets \code{ends\_on} to the new last day and \code{ended\_early} and recomputes \code{days\_lent}, freeing the Person from the next day; the shortened Loan stays in the constraint for the days it lent.

\field{Purpose}
Ledger keeps every Team's Account and the append-only record of Transactions, prices lines, and computes Refunds. It knows credits only: it holds no capacity information and never decides whether a line can be allocated.

\field{Responsibilities}
\begin{itemize}
\item Accounts and Statements (\req{Ledger.Account}); four Transaction kinds, append-only (\req{Ledger.Transaction.Kinds}, \req{QA-audit}); Grants, spend order, and rollover (\req{Ledger.Grant.Period}).
\item The Quote formula, also used while drafting (\req{Ledger.Price.Formula}, \req{Draft.Quote.Line}), with the Stretch tier premium and demand surcharge (\req{Metered.Tier.Define}, \req{Ledger.Surcharge}), and the Refund step function (\req{Release.Refund}).
\item Earnings and their correction after an early end (\req{Ledger.Earning.Post}, \req{Release.Loan.Prorate}), posted with Charges inside the caller's transaction (\req{CO-tx}).
\end{itemize}

\field{Provided interface}
\begin{lstlisting}[language=Java]
final class Pricing {                                       // pure, no Spring, no database
  static Quote quote(LineSpec line, TypePricing pricing, BigDecimal priorityPremium, BigDecimal peakFill);  // sum over hours of quantity x unitPrice x band, x premiums, x surcharge
  static Credits refund(Credits charge, RefundSchedule schedule, Duration leadTime);  // step function, never 100%
  static Credits attributable(Credits lockedQuote, LineSpec line, LineSpec part, TypePricing pricing);  // a released part's share of the locked Quote
}
interface LedgerService {
  AccountView account(TeamId team);                         // (read-only) granted, earned, held, balance, available
  void requireAffordable(TeamId team, Credits requiredSum); // no lock, early refusal; throws RuleViolation("INSUFFICIENT_BALANCE")
  void holdCredits(TeamId team, RequestLineId line, Credits quote);     // held += quote (locks account row, repeats the check)
  void releaseCredits(TeamId team, RequestLineId line);                 // held -= that line's quote
  void commitCharges(RequestId request, List<ChargeSpec> charges);      // for each line: held -> Charge, granted first then earned, split recorded
  void postEarning(EarningSpec earning, Actor actor);                   // earned += amount; spec: lending Team, Loan, line, amount, description
  void refund(TeamId team, RequestLineId line, Credits amount);         // returns in the Charge's proportions; 0.00 posts nothing
  void correctEarning(TeamId lendingTeam, LoanId loan, Credits delta, String description);  // only Transaction that may make Balance negative
  void postGrant(TeamId team, PeriodId period, Credits amount, String reason, Actor actor);  // PLANNER or rollover
  void rollover(PeriodId ending, PeriodId starting);        // expire granted, record on Statement, post planned Grants; idempotent (no-op if already rolled)
  Statement statement(TeamId team, PeriodId period);        // (read-only) own Manager or PLANNER
}
\end{lstlisting}
\code{Pricing} is pure. \module{Requests} calls \code{quote} while drafting and at submission, when the result is locked on the line. \code{LineSpec} gives the quantity (instances or units), the occurrences in the firm's time zone, the Priority mark, and the tier premium (1 without a tier). With $q$ the quantity, $p$ the Unit Price, $b(h)$ the multiplier of the Price Band containing hour $h$ (1.0 if none), $\pi$ the priority premium for a Priority line (1 otherwise), $\tau$ the premium of a Metered line's service tier (1 otherwise), and $\sigma = 1 + r \cdot f$ the demand surcharge, $r$ the type's surcharge rate (0 when off) and $f$ the peak fill, between 0 and 1, that \module{Requests} reads from \code{AllocationQueries.peakFill} over the line's occurrences, the line's own rows not counted (0 for a Matched line):
\[ \textit{Quote} = \pi \cdot \tau \cdot \sigma \cdot \textstyle\sum_{\mbox{\scriptsize occurrence } o}\ \sum_{\mbox{\scriptsize hour } h \in o}\ q \cdot p \cdot b(h). \]
The premiums and the surcharge multiply the whole line, so \code{attributable}, the share of the locked Quote a released part carries (its band-weighted hours over the line's), needs neither, and the fill is never stored. The share uses the Price Bands in force at the Release, since only the locked Quote is stored, so only a band change after submission makes it drift. Credits carry two decimals; a Quote is rounded half-up once per line. \code{refund} takes the step with the largest lead time not above \code{leadTime} and returns that fraction of \code{charge}, rounded down; a part of an occurrence already started returns 0. \module{Settings} refuses any step of 100\% or more and \code{refund} asserts it.
% NOTE: brief section 4 calls Credits "integer credits" while section 7 stores numeric(12,2). We use two decimals so that
% a 25% Refund of 45 credits is exact; with integers the rule would be "round Refunds down to whole credits".

\code{LedgerService} keeps granted, earned, and held credits per Team in \code{account}; Balance is granted plus earned, Available Balance is Balance minus held. Every change first locks the account row (\code{SELECT ... FOR UPDATE}, inserting it if missing, so \module{Members} never calls Ledger), after the type locks and until commit, so two Requests of one Team never see the same Available Balance. Other Teams' accounts (lending or Bumped Teams) are locked when reached; the rare cycle this allows ends in a deadlock abort, retried once.

\field{Required interfaces}
\module{Settings}: \code{SettingsService.current} (pricing, premium, Period, planned Grants). \module{Members}: a Team's Manager, for Statement scoping. \module{Notifications}: \code{Notifier.notify}, by \code{rollover} (granted credits expired, new Grant posted; scenario S7) and by \code{postGrant} for a mid-Period Grant.

\field{Data owned}
\code{account(team\_id, granted, earned, held)} and \code{transaction(id, team\_id, kind, amount, granted\_part, earned\_part, period\_id, line\_id, loan\_id, corrects\_id, actor\_id, posted\_at)}, kinds \code{GRANT}, \code{CHARGE}, \code{EARNING}, \code{REFUND}, amounts positive except a correction, \code{actor\_id} null for a job. Added to the brief: \code{transaction.reason} (mid-Period Grants), \code{held\_credit(line\_id, team\_id, amount)} (a line's held amount without reading Requests' tables), and \code{period\_close(team\_id, period\_id, expired, closing\_granted, closing\_earned, closed\_at)}. \code{transaction} is append-only by grant, not convention: Flyway migrates as the schema owner, the application role has only \code{INSERT} and \code{SELECT} on it, and a correction is a new row naming the corrected one in \code{corrects\_id}.

\field{Invariants}
\begin{itemize}
\item Granted and held credits are never negative; the Balance is never negative except after an Earning correction.
\item Held credits equal the Team's \code{held\_credit} rows, which equal the locked Quotes of its Held lines.
\item The account row equals the fold of the Team's Transactions and \code{period\_close} rows (a test recomputes it).
\item A Charge equals its locked Quote and its two parts sum to it, granted first; a line's Refunds stay within its Charge, in its proportions. Transaction rows never change.
\item \code{rollover} is idempotent: rolling into a Period already rolled into is a no-op (the key of \code{period\_close}), so the start-up catch-up in \module{Jobs} is safe.
\end{itemize}

\field{Failure behavior}
\code{INSUFFICIENT\_BALANCE} is the refusal a Manager sees, with the shortfall. After a correction makes the Balance negative, the Available Balance is negative too, so every Request with a priced Required Exclusive or Metered line is refused until a Grant or Earning restores it; a Required sum of zero, such as a Request of Matched lines only, is never refused. The methods join the caller's transaction, so a failed Charge rolls back the commit of every Hold (\req{CO-tx}). \code{UPDATE} or \code{DELETE} on \code{transaction} fails with SQLSTATE 42501.

\field{Information hiding}
Callers see \code{Credits}, \code{AccountView}, and \code{Statement}; the granted and earned split, the spend order, rounding, and held amounts per line are hidden, so the Stretch demand surcharge is one more multiplier inside \code{Pricing}.

\field{Worked examples}
\emph{Quote.} A room at Unit Price 10 for Thursday 14:00 to 17:00 on October 15, 22, and 29: every hour lies in the weekday band ($\times1.5$), so an hour costs $1 \times 10 \times 1.5 = 15$, an occurrence 45, and the Quote is $3 \times 45 = 135$; as a Priority line, $135 \times 2 = 270$. From 16:00 to 19:00 an occurrence would cost $15 + 5 + 5 = 25$, the last two hours being outside the band ($\times0.5$).
\emph{Refund.} Schedule: 75\% at seven days or more, 25\% under seven days, 0\% once started. The 135-credit line is released on Monday, October 19 at 10:00. October 15 is consumed. October 22 (Charge 45) starts in 3 days 4 hours: $45 \times 0.25 = 11.25$. October 29 starts in 10 days 4 hours: $45 \times 0.75 = 33.75$. One Refund of 45.00 posts.
\emph{Spend order.} Granted 30 and earned 50 meet a Charge of 40: \code{granted\_part} 30, \code{earned\_part} 10, leaving 0 and 40. A later Refund of 20 on that line returns 15 to granted and 5 to earned.

\field{Responsibilities}
\begin{itemize}
\item Suggestions (\req{Suggest.Create}, \req{Suggest.Accept.Existing}); Drafts, Quotes, and submission (\req{Draft.Create}, \req{Draft.Line.Add}, \req{Draft.Line.Required}, \req{Draft.Quote.Line}, \req{Draft.Submit.Lock}).
\item The state machine and its history (\req{Lifecycle.States}, \req{QA-audit}); evaluation, Holds, and the Objection Window (\req{Lifecycle.Evaluate}, \req{Lifecycle.Hold.Place}, \req{Lifecycle.Window.Start}).
\item Allocation in one transaction and re-evaluation of Waiting Requests (\req{Lifecycle.Allocate}, \req{QA-atomic}, \req{Lifecycle.Waiting.Reevaluate}); replacement, escalation, and the Capacity Planner's escalation list (\req{Matched.Refuse.Replace}, \req{Matched.Escalate}, \req{Planner.Settings}).
\item Entry points for Release and an early Loan end (\req{Release.Line}, \req{Release.Loan.Prorate}).
\end{itemize}

\textbf{\code{RequestLifecycleService}} is the orchestrator: one \code{@Transactional} method per transition, retried once after a deadlock or lock timeout, always in this order: (0) lock the Request row (\code{SELECT ... FOR UPDATE}), so two transitions of one Request run one after the other; (1) lock the Resource Types of its own lines with one ascending \code{AllocationLock.lockTypes}; a waitlist fill may then lock a waiting Request's other types, the one path that can take a type after an account, covered by the retry (Section~\ref{sec:runtime}); (2) lock the Team's account row through the first locking Ledger call (\code{holdCredits} or \code{commitCharges}), never a type after an account outside that fill; (3) read; (4) write; (5) \code{record}; (6) \code{Notifier}, whose rows share the transaction, so a rolled-back transition tells nobody. \code{requireAffordable} at submission reads the account without a lock, before (0), only as an early refusal. A Bump at submission locks, after the types, the Bumped Requests in id order and then the accounts in ascending Team id, which breaks the Request-first order and so also relies on the retry.

\textbf{Private steps.}
\begin{description}[leftmargin=0pt,font=\normalfont\ttfamily]
\item[evaluateAll] \code{evaluate} every line; a misfit Priority line, or Metered line with a tier, asks \code{planBump}, and a plan counts as a fit. A misfit's reason is kept in the line's \code{request\_event} note.
\item[placeHolds] Only while the window runs: Required, then affordable Optional lines; \code{applyBump} where planned, \code{hold}, \code{holdCredits}. Lines are taken Required first, then in line order, and each is evaluated, and its Bump planned, again just before its Hold, so lines of one Request that compete for the same capacity, two Required Priority lines among them, see each other's Holds and Bumps. A Required line that no longer fits joins its Waitlist, and the other lines keep their Holds. When the Request allocates at submission without a Hold first, a Required line that no longer fits cancels the Request's own Holds and the Request goes to Waiting; Bumps already applied stand, with their Refunds, and the capacity they cleared is offered to the Waitlist, where the Bumped lines come first.
\item[routeApprovals] \code{ApprovalDriven.select} for named Persons at submission and for the Manager's picks.
\item[allocate] Always in this order. (a) Re-run \code{evaluateAll} under the locks; an Approved Candidate who is no longer eligible makes the line \code{UNSATISFIABLE(NOT\_A\_CANDIDATE)}, and the system refuses that approval. If a Required line fails, \code{toWaiting} runs instead, before any commit, and a replacement is asked. If the Balance no longer covers the Required Charges (after a rollover or an Earning correction while Pending), \code{toWaiting} runs instead with reason \code{INSUFFICIENT\_BALANCE}; the approval is kept. (b) Drop unfit or unaffordable Optional lines, and Optional Matched lines refused with no Candidate left, with the reason; an Optional Matched line still awaiting selection or approval stays open. (c) Apply Bump plans, then \code{Allocator.commit} each Exclusive and Metered line (HELD to ALLOCATED). (d) \code{LedgerService.commitCharges}. (e) \code{MatchedAllocator.commit} each approved Matched line, forming the Loans; it repeats the eligibility check only as a guard that throws \code{ALLOCATION\_CONFLICT} and rolls back the transition. (f) \code{postEarning} per Loan from \code{loansFor(line)}. (g) Set the Request Allocated, \code{record}, and notify the Manager and each Person through \code{Notifier}. When the last approval of an open Optional Matched line arrives after allocation, \code{decideApproval} runs (e) and (f) for that line alone, in its own transaction.
\item[toWaiting] \code{cancel} and \code{releaseCredits} for Held lines; \code{join} for unsatisfied Required lines, including a Required line whose Hold a lapse or refusal released and that no longer fits, so a Waiting Request always has a line on a waitlist; approvals stay; \code{onCapacityFreed}.
\item[onCapacityFreed] For each line from \code{waitingFor(type, window)}, in order: allocate its Request, Waiting or Pending, if every Required line fits at once and is approved; if only approvals are missing and the window runs, back to Pending with \code{placeHolds}; else next. The fill acts as the system: its events and Charges carry a null actor, so the releasing Manager never appears on the filled Team's Statement.
\item[record] Insert a \code{request\_event}; a null actor is the system (jobs).
\end{description}

Waiting & \code{reopenForEdit} & Team's Manager; no line Allocated, PartlyReleased, or Loaned & Draft & \code{Allocator.cancel} on every line; Quotes unlocked \\
Allocated & Bump by another Request & Bumped line Required & Waiting & Full Refund; line Allocated to Bumped to Waiting, two events with reason \code{BUMPED}, \code{request\_line.bumped} set; line at the head of its waitlist; other lines stay \\
Allocated & Release, early Loan end & none & Allocated & Refund or Earning correction; \code{onCapacityFreed} \\
Allocated & approval, refusal, or lapse on an open Optional Matched line & none & Allocated & last approval: Loan formed, \code{postEarning}; refusal: replacement asked, or the line Dropped if no Candidate is left; lapse: \code{escalate} only \\
Draft, Pending, Waiting & \code{withdraw} & Team's Manager; from Waiting, no line Allocated, PartlyReleased, or Loaned & Withdrawn & \code{Allocator.cancel} on every line; held credits released \\
\end{longtable}}

\textbf{Line states.} Draft, then Evaluated. Exclusive and Metered: Held, Allocated, Released or PartlyReleased; Held to Evaluated when a lapse releases the Hold, then Waiting if a Required line no longer fits; Allocated (or Held) to Bumped to Waiting in one transaction. Matched: AwaitingApproval, Approved, Loaned, or Refused (note \code{REPLACEMENT\_NEEDED}) and back to AwaitingApproval on replacement; an Optional line refused with no Candidate left is Dropped (note \code{APPROVAL\_REFUSED}). Optional lines may be Dropped; withdrawal Cancels every line. A waiting line whose start passes leaves the waitlist with the note \code{WINDOW\_STARTED} and stays Waiting (\code{expireWaitingLines}); its Manager is not notified. \code{request\_line} keeps the window and units as submitted; what a line holds now is in \module{Allocation}'s rows, shown as \code{allocatedParts}.

\textbf{Window, escalation, Release.} \code{window\_ends\_at} is set at submission when any line needs approval (the Request then enters Pending, or, if only Optional lines need approval, Allocated or Waiting), to that instant plus \code{objectionWindowWorkingDays} Monday-to-Friday days (example default 2, so a Request submitted on Friday at 10:00 lapses on Tuesday at 10:00), and is never reset: a Request reopened and submitted again keeps its window, and one whose window has lapsed goes to Waiting. When no line needs approval at submission, such as a Required Person line whose Shortlist is too short, no window is set and the Request goes to Waiting, so a later selection cannot bring it to Pending; \code{placeHolds} does nothing after it. Each minute \code{DueWorkJob} asks \code{lapsedWindows(now)} and calls \code{onWindowLapse} per Request in its own transaction. \code{onWindowLapse} is idempotent: a Request with no unescalated Outstanding approval is skipped, so a repeated run notifies nobody twice. For a Pending Request it runs \code{toWaiting}, releasing every Hold and its credits, then \code{escalate}; for a Waiting Request, such as one whose approval was left Outstanding after a refusal, it runs \code{escalate} only, so that \req{Matched.Escalate} holds after a refusal; an Allocated Request with an Optional approval Outstanding likewise gets \code{escalate} only. \code{escalate} sets \code{escalated} on every Outstanding approval and hands it to every Capacity Planner, who decides from \code{escalations()}; from then on only a moment when every Required line fits at once allocates the Request. \code{releaseLine} calls \code{Allocator.release}, prices each piece given back as its share of the locked Quote (\code{Pricing.attributable}), applies \code{Pricing.refund} per occurrence with the lead time to that occurrence's start, posts one \code{refund} (none for 0.00), and runs \code{onCapacityFreed}; \code{previewRelease} answers the same Refund without writing, for the screen to show before the Manager confirms. The body names its kind: \code{WHOLE}, \code{EARLIER\_END} with \code{newEnd}, \code{OCCURRENCES} with their starts, or \code{FEWER\_UNITS} with \code{newUnits}, the units kept. A whole-line Release after the first occurrence started gives back only the occurrences not yet started, and the line becomes PartlyReleased. \code{endLoanEarly} calls \code{LoanService.endEarly}, posts \code{correctEarning} for the lost days at the Loan's net Earning per day lent, so a later Day Rate change has no effect, and notifies the Person and the lending Manager.

\field{Required interfaces}
\module{Allocation}: all of its interfaces. \module{Ledger}: \code{Pricing}; \code{LedgerService} except \code{postGrant}, \code{rollover}, \code{statement}. \module{Inventory}: \code{InventoryQueries.type}. \module{Members}: \code{summary}. \module{Settings}: \code{current}. \module{Notifications}: \code{Notifier.notify}.

\field{Data owned}
{\raggedright
\begin{itemize}
\item \code{request(id, team\_id, state, submitted\_at, window\_ends\_at)}.
\item \code{request\_line(id, request\_id, type\_id, allocation\_class, quantity, units, starts\_at, ends\_at, recurrence, required, priority, named\_resource\_id, named\_member\_id, skills, tier\_id, tier\_premium, locked\_quote, bumped, state)}: \code{recurrence} the number of weekly occurrences (2 to 52, Exclusive only), \code{skills} a \code{bigint[]} of skill ids, \code{tier\_id} a Metered line's service tier and \code{tier\_premium} its premium locked at submission, \code{bumped} the Bumped mark, kept when the line leaves the waitlist and joins it again.
\item \code{suggestion(id, member\_id, team\_id, manager\_id, proposal..., recurrence, skills, state, accepted\_line\_id, reason, decided\_by, decided\_at)}, the proposal columns mirroring a line plus a note; \code{manager\_id} the addressee when made.
\item \code{request\_event(id, request\_id, line\_id, from\_state, to\_state, actor\_id, at, note)}.
\end{itemize}}
\field{Invariants}
\begin{itemize}
\item A Request is in exactly one state; every Request or line state change writes a \code{request\_event} in the same transaction.
\item \code{locked\_quote}, \code{tier\_premium}, and \code{submitted\_at} are set at submission and cleared only by \code{reopenForEdit}; \code{window\_ends\_at} never changes once set, and Held lines exist only in a Pending Request before it.
\item Lapse is judged by the injected \code{Clock}, not by the job: \code{decideApproval} compares \code{window\_ends\_at} with now, so an approval arriving after the window ended is treated as lapsed (\code{WINDOW\_LAPSED} for the lending Manager, no Hold kept) even before \code{onWindowLapse} has run.
\item An Allocated Request had every Required line Allocated or Loaned when it entered the state; its only open lines are Optional Matched lines awaiting selection or approval. Only Optional lines are Dropped; only Required lines wait.
\end{itemize}

\field{Failure behavior}
Any exception rolls back the whole transition, notifications included. A \code{RuleViolation} becomes \code{problem+json} with its \code{code} (409 state conflict, 422 invalid input); a deadlock or lock timeout, after one retry, \code{ConcurrencyRetryException} (503). A failed job call is logged and retried next minute; other Requests proceed in their own transactions.

\field{Information hiding}
The state machine, the private steps, and the lock order are internal to \code{RequestLifecycleService}. Controllers and jobs call one method per transition and cannot run a step alone, so no caller can commit Holds without posting their Charges.
