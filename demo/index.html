The story in one paragraph

OpenBench lets a Manager post one Request for people, rooms (Exclusive), and compute (Metered), and settles it in credits. We wrote 91 functional test cases from the SRS. Jai runs four of them by hand in the real app. Brian shows that those same cases, and all the others, run automatically on every build, and that the run report traces each requirement to its cases. Fotih shows how much of the code those tests reach. Yerassyl shows how a defect the tests exposed went through the tracker, from report to closed.

Section summaries

1–2. Opening and live test cases Jai

One world, reset just before the demo. Four signed-in users in four tabs: alice (Platform), bob (Research), oscar (Operations), erin (Capacity Planner). Each act names its test case, does the steps, and points at the expected result on screen.

  1. Quotes (TC-DRF-03): a room line costs 30.00 and a GPU line 50.00, from the price formula.
  2. No overspending (TC-DRF-07): bob's 660.00 Request is refused, "short by 60.00 credits"; making a line Optional lets it through.
  3. No double-booking, Release, and the waitlist (TC-EXC-01, TC-REL-01, TC-EXC-05): bob waits for alice's room; alice releases it for a 22.50 Refund; bob's Request is allocated automatically.
  4. Priority Bump (TC-EXC-07, TC-EXC-08): alice's Priority line bumps oscar's room booking; oscar gets a full Refund and heads the waitlist; withdrawing is refused. That refusal was bug #27, which Yerassyl shows later.
  5. Dashboard (TC-DSH-01), only if time allows.

3. Automated tests and the run report Brian

The test case document (the PDF) shows TC-EXC-08 as written. In the code, BumpCasesTest carries @Verifies("exc-bump-effect") and asserts each step's expected result. Brian runs it live (about 11 s), then opens the run report: every case, its tests, and its status, plus all 47 requirements marked Passed. He also shows the cases nobody can run by hand: two Managers submitting at the same instant, and clock steps such as an Objection Window lapsing.

4. Code coverage Fotih

The JaCoCo report from mvn verify: 97.1% of lines and 87.0% of branches over the server's 5,868 lines. Fotih says which tests produced it (all 730), what is measured (the server's main code; only the main() class is excluded), and where coverage is weakest (common and security branches). Then he makes the build fail by raising the branch minimum to 90%, and shows the client's Vitest report.

5–6. Issue tracking and close Yerassyl

GitHub Issues on JaiNana123321/openbench, milestone Release 1. Labels carry the status: planned, ready, in progress, in review, blocked, closed. Yerassyl walks through #27 from report to close: blocked on a decision, in progress, in review, then closed with links to the fixing commits. He also shows #18 and #19, two defects that test cases found, and #17, the log of spec changes. He closes with what isn't done: the non-functional gaps (Docker image, HTTPS, performance not measured).

Before the demo

Tonight Jai

  • Pull main (at 578798c). Start Docker.
  • Run mvn verify (about 2 min), then npm --prefix web run coverage.
  • Copy the reports somewhere a later test run can't overwrite them (a single-class mvn test rewrites the run report with only its own cases): 
    mkdir -p ~/demo2-reports
cp -R target/site/jacoco ~/demo2-reports/jacoco
cp target/test-cases/report.md ~/demo2-reports/
cp -R web/coverage ~/demo2-reports/web-coverage
  • Rehearse section 2 once on a fresh world (steps on Jai's page).

15 minutes before

  • Reset the world: docker compose down, then mvn spring-boot:run -Dspring-boot.run.profiles=demo; wait for "Started OpenBenchApplication".
  • Sign in the four users (password demo), one per address, so their sessions don't collide (details on Jai's page).
  • Open, each in its own tab or window: the test case PDF, VS Code on BumpCasesTest, ~/demo2-reports/report.md in VS Code preview, ~/demo2-reports/jacoco/index.html, ~/demo2-reports/web-coverage/index.html, a terminal in the repo, and GitHub Issues.
  • Browser zoom at 125%; notifications and chat apps off.

If something breaks

  • A live step fails: say what should have happened, then move on. Every case on screen also has a passing automated test, which Brian shows next.
  • The app won't start: Brian starts early and runs BumpCasesTest, then the run report. That covers the same cases.
  • No network: the tracker section needs GitHub. Have screenshots of #27 (the issue and its timeline) on the laptop.
