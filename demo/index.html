OpenBench

An internal resource marketplace. A Team's Manager posts one Request for people, Exclusive resources such as rooms, and Metered capacity such as GPU hours. The system allocates each line under the policy of its Allocation Class and settles it in credits.

    Talking points
    • Step 3: the last-room race is tested. Two concurrent submits for the last free room: exactly one wins (AllocationConcurrencyTest, SubmitConcurrencyTest).
    • Step 5: the two refusal reasons come from different allocators. The Exclusive allocator finds no free room; the Metered allocator checks Pool Capacity and the Quota for every hour of the window.
    • Fallback if the live app fails: run mvn test -Dtest=SubmitEndToEndTest. It runs this same story against PostgreSQL 16.

    Challenges we expect

    Time-driven behaviour
    Objection Window lapses and Period rollover depend on the clock. The design tests them with a moved clock and finds due work by query, so a missed run catches up.
    Lock order
    Matched lines add Loans to the transaction. Every path must keep taking type locks in ascending order, or we risk deadlocks or an oversold pool.
    Client and API drift
    More screens means more endpoints. Generating client types from the OpenAPI document makes a changed endpoint fail the TypeScript build.
    Scope for four students
    Release 1 is fixed. Every Stretch item is an extension point and never a precondition.
