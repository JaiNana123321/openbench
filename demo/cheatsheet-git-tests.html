Sections 4 and 5 cheat sheet: Git and tests

About 2 minutes · Version control 15% + Testing 15%. Italics = say it. Blue = what's on screen.

Before you start

  • Run mvn verify once earlier in the day. The first run downloads the PostgreSQL image and is slow.
  • Have a terminal open in the openbench folder, and a browser tab on the GitHub repo.

Part 1: Version control

  1. In the terminal, run:
    git log --graph --oneline -25 Branch lines joining main at each "Merge branch 'feature/…'" commit.
  2. "Each feature was built on its own branch and merged into main. There are 7 feature branches and 53 commits from 15 to 21 October."
  3. Point at one branch, for example feature/allocation: "Each branch adds the code, then its tests, then merges. Here are two code commits followed by two test commits."
  4. Read one commit message out loud, for example "Test the guard, the type lock, the registry, and the race for capacity". "Messages say what changed, so the history reads like a changelog."
  5. In the GitHub tab, open Branches to show the pushed branches.
  6. "The spec (SRS, design doc, ADRs) is in a separate repo, swe_csds393. The code repo keeps a pinned copy."

The 7 branches, in order

  1. feature/web-foundation: React app, sign-in, layout
  2. feature/backend-foundation: Spring Boot, database schema, login, ArchUnit
  3. feature/inventory: Resource Types and Resources
  4. feature/settings-ledger: prices, Grants, Accounts, Statements
  5. feature/requests-draft: Drafts, lines, Quotes
  6. feature/allocation: room and GPU allocators, the Waitlist
  7. feature/submit-lifecycle: Submit, Withdraw, Request detail

Part 2: Testing

  1. Run the back-end tests:
    mvn verify BUILD SUCCESS, with the test counts.
  2. "258 JUnit tests on the back end. They run on a real PostgreSQL 16 that Testcontainers starts in Docker, using our real migrations."
  3. Run the front-end tests:
    cd web && npm test 13 test files, 68 tests passing.
  4. "68 Vitest tests on the React screens: each page renders for the right roles and shows the server's error messages."
  5. Open src/test/java/edu/cwru/openbench/allocation/AllocationConcurrencyTest.java. "This test makes two threads race for the last free room. Exactly one wins, every time. It's a repeated test."
  6. Show a test display name with a requirement id, for example "Metered.Pool.Check: is POOL_FULL at 14:00, one unit short". "Test names carry the SRS requirement ids, so we can trace every requirement to its tests."
  7. "ArchUnit fails the build if a module breaks our layer rules."

Kinds of tests (if asked)

  • Unit: pure rules such as pricing, time windows and the hourly GPU check.
  • Integration: services and REST endpoints on PostgreSQL.
  • Database: migrations, the no-overlap constraint, and the append-only permissions.
  • Concurrency: races for the last room and the last GPU units.
  • Architecture: ArchUnit module rules.
  • End to end: SubmitEndToEndTest runs the whole live demo story.

If the grader asks

  • "Why not an in-memory database for tests?" Our no-double-booking rule is a PostgreSQL exclusion constraint. H2 can't check it, so the tests would prove nothing.
  • "Do the tests run automatically?" They run with mvn verify on every build. Adding GitHub Actions so they run on every push is our first next step.
  • "How do you collaborate?" Feature branches merged into main. Next increment, every merge goes through a pull request reviewed by a teammate.
