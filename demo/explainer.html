How OpenBench works

A plain-language guide to the idea, the vocabulary, and the hard parts. Built means it's in Demo 1. Next means it's designed but not built yet.

The idea

Inside a company, teams compete for the same things: people with the right skills, rooms and lab instruments, and compute like GPU hours. Today each is booked in a different place, with no shared rules.

OpenBench is one internal marketplace for all of them:

  • A team's Manager writes one Request that can ask for a person, a room, and GPU time together.
  • The system allocates each part by the rules for that kind of resource.
  • Everything is paid for in credits from the team's budget. Credits are for visibility ("showback"), not real money.

Example: "For Tuesday's workshop, Platform needs Room A from 14:00 to 16:00 and 4 GPUs for two days." That is one Request with two lines.

Resource types

Every resource has a Resource Type (for example "Meeting room" or "GPU"). An Administrator creates types as data in the app, so adding a new kind of resource needs no code change. Each type belongs to one of three Allocation Classes, which decide how it is handed out:

A Request's life

  • A Request has one or more lines. Each line is a type, a quantity, and a time window.
  • Each line is Required or Optional. The Request succeeds only if every Required line can be given. Optional lines never block it.
  • While drafting, each line shows a Quote: its price in credits, worked out by the server.
Draft ──Submit──▶ Submitted ──▶ Allocated (every Required line fits) └──▶ Waiting (something is taken; lines join the Waitlist) Draft or Waiting ──Withdraw──▶ Withdrawn
  • Submit locks the Quotes, so the price can't change afterwards. It's refused if the team can't afford the Required lines, and the refusal says how many credits short it is.
  • Waitlist order: bumped lines first, then Priority lines, then by submission time.
  • Next Pending: when a Request includes a person, it waits for the lending Manager's approval. Meanwhile the room and GPUs are put on Hold (reserved but not charged) for a limited time, the Objection Window.

Credits and pricing

  • Each Team has an Account. The Capacity Planner gives it a Grant every Period (one month). In the demo, Platform gets 5,000, Research 600, and Operations 1,000.
  • Balance = granted + earned credits. Available = Balance minus credits held for pending work.
  • Price = Unit Price × hours × the Price Band multiplier. Weekdays 09:00–17:00 cost ×1.5, weekends ×0.5, and other hours ×1.0.
    Example: Room A on Tuesday 14:00–16:00 costs 10 × 2 h × 1.5 = 30 credits.
  • A charge spends granted credits first, then earned ones. Unused granted credits expire at the end of the Period.
  • Next Teams earn credits when they lend a person. Releasing a booking early refunds a share: 75% if it's at least 7 days ahead, otherwise 25%.

How we built the hard parts

1. Two people booking the last room at the same moment

If two Managers submit at the same instant, both could see Room A as free and both book it. We stop this in two ways:

How we did it
  • The database refuses overlaps. The exclusive_occurrence table has a PostgreSQL exclusion constraint: no two active bookings of the same resource may have overlapping time ranges (EXCLUDE USING gist). Even buggy Java code can't double-book a room.
  • One submit per Resource Type at a time. Before checking anything, a submit locks the row for each Resource Type it touches (SELECT … FOR UPDATE). A second submit for the same type waits until the first finishes, then sees the up-to-date picture.

2. Sharing a GPU pool fairly

A GPU pool can be split, so "no overlap" doesn't apply. The rule is that in every hour, the units in use must not exceed the pool, or the team's Quota.

How we did it
  • A query sums the units already used (allocated or held) for each hour of the requested window.
  • A small pure function (HourlyLoad) finds the first hour where the new line wouldn't fit. It reports POOL_FULL or QUOTA_EXCEEDED with that hour.
  • A database constraint can't express a sum, so this check relies on the same type lock as above. Nobody can change the pool between the check and the write.
  • The same check guards the Resource Owner: shrinking or retiring a GPU node is refused if future bookings would no longer fit.

3. Avoiding deadlocks and stuck waits

How we did it
  • Locks are always taken in the same order (ascending type id). Two transactions can't each hold a lock the other wants, so they can't deadlock on type locks.
  • Every allocating transaction sets a 5-second lock timeout, so it never waits forever.
  • If a submit hits a timeout or deadlock, it is retried once in a fresh transaction. If that fails too, the user gets "try again" (HTTP 503), and nothing has changed.

4. Never spending more credits than a team has

How we did it
  • Charging or holding credits locks the team's account row first, then checks the Available balance. Two submits from one team can't both spend the same credits.
  • The account totals always equal the sum of the team's transactions, and the tests check this.

5. History that can't be rewritten

How we did it
  • Credit transactions, Request history, and the settings change log are append-only. The database account the app connects as is not granted UPDATE or DELETE on those tables. It's enforced by permissions, not just by convention.

6. Who can see and do what

How we did it
  • Session login with CSRF protection (the browser sends a token from a cookie back in a header).
  • Every write checks the role. Without it the answer is 403 Forbidden, and nothing changes.
  • A Manager asking for another team's Request or Statement gets 404 Not Found, so the app doesn't reveal that it exists.

7. Keeping prices honest

How we did it
  • Quotes are only ever computed on the server. The React client fetches them and never does its own math, so the Quote you see is exactly the one that gets locked.
  • Prices are rounded once per line (half-up, to 2 decimals). Refunds round down.

Architecture in one minute

  • One app, one database: a Spring Boot (Java) back end, PostgreSQL 16, and a React + TypeScript front end served by the same app. This is a "modular monolith".
  • Modules: members, inventory, settings, ledger, allocation, and requests are built. notifications, dashboard, and jobs come next.
  • Module rules: a module only calls the modules below it and only writes its own tables. An ArchUnit test fails the build if anyone breaks this.
  • Database changes are versioned scripts run by Flyway at startup.
  • Tests run on a real PostgreSQL 16 started by Testcontainers. An in-memory database couldn't check the exclusion constraint or the locks.
