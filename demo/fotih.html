Fotih: code coverage

18:00–24:00 · Code coverage, 30 points. The rubric asks for four things. Show a coverage report made by a tool. Say which tests produced it, which code was measured, and what the figures mean. This page follows that order.

Purple italics is what to say. Blue is what should be on screen.

What to have open

  • ~/demo2-reports/jacoco/index.html (server report, JaCoCo)
  • ~/demo2-reports/web-coverage/index.html (client report, Vitest)
  • pom.xml in VS Code, lines 27–28
  • A terminal in the repo, font size up

1. The report 18:00–19:00

  1. Open the JaCoCo report. Bottom row "Total": Instructions 96% (1,202 of 35,822 missed), Branches 86% (305 of 2,343 missed), Lines 169 of 5,868 missed, Methods 40 of 1,705 missed, Classes 0 of 307 missed.
  2. This is JaCoCo, the standard Java coverage tool. mvn verify generates it on every full build. Over the server, 97.1% of lines and 87.0% of branches were executed by at least one test. The page shows 86% because JaCoCo cuts off the decimals: it's 86.98% exactly.

2. Which tests produced it 19:00–19:45

  • All 730 server tests, in 103 classes. Maven runs them with a JaCoCo agent attached, which records every line and branch they execute.
  • Most are integration tests: a real HTTP request goes in, through our controllers and services, to a real PostgreSQL database in a Docker container. So a covered line ran the way it runs in production, not against a mock.
  • They include the 161 tests tied to the functional test cases Brian showed, plus unit tests and concurrency tests.

3. Which code was measured 19:45–20:30

  • Measured: all of the server's own code in src/main/java: the nine modules (requests, allocation, ledger, and so on) plus common, security, and config. That's 307 classes and 5,868 lines.
  • Excluded on purpose: one class, OpenBenchApplication. It only holds main(), which tests never call, because the test framework starts the server itself.
  • Not in this report: test code itself, and the React client, which has its own report (step 6). SQL in our migrations isn't Java bytecode, so JaCoCo can't see it. The database rules are tested by the integration tests instead.

4. What the figures mean 20:30–22:00

  1. Lines: a line counts as covered if any test executed it. Branches is stricter: for every if, did tests take both the true and the false side? That's why branches (87%) are lower than lines (97%).
  2. Point at the package list. Branch column, lowest: common 68%, security 73%. Highest: jobs and config 100%, dashboard 97%. The largest module, requests, shows 84% of 924 branches.
  3. Click edu.cwru.openbench.security → LoginHandler → LoginHandler.java. Yellow diamonds on lines 64, 74, and 78: one side of each branch never ran. Yellow means half-covered. These are defensive branches: an unusual login failure type, a missing username, and a username over 64 characters, which we cut so nobody can forge log lines. Tests never send those, so the branch shows yellow.
  4. Back, then edu.cwru.openbench.common → DateRange → DateRange.java. Lines 23 and 27 in red: contains(…) never ran at all. Red means no test executed it. Coverage is how we find this: these methods may simply be unused, so they're candidates to delete rather than to test.
  5. Coverage says what ran, not that it's right. That's why we pair it with the functional test cases, which check the expected results.

5. The coverage gate 22:00–23:00

  1. Show pom.xml lines 27–28. coverage.line.minimum 0.90 and coverage.branch.minimum 0.80 The build fails if coverage drops below 90% of lines or 80% of branches. So nobody can merge a feature without tests and not notice.
  2. Prove it. In the terminal: 
    mvn jacoco:check@check -Dcoverage.branch.minimum=0.90
    About 1 second: "Rule violated for bundle openbench: branches covered ratio is 0.86, but expected minimum is 0.90", then BUILD FAILURE. I raised the branch minimum to 90% and the build fails. JaCoCo rounds 86.98% down to 0.86 in that message.

6. The client report 23:00–24:00

  1. Open the Vitest report. Statements 95.49%, Branches 83.66%, Functions 96.61%, Lines 97.96%.
  2. The React client has 229 tests in 46 files, using Vitest and React Testing Library, with the API mocked. Its own thresholds in web/vite.config.ts are 90% statements, 78% branches, 92% functions, and 92% lines. Only main.tsx, which just mounts the app, and the test helpers are excluded.

If the grader asks

"Why not 100%?"
The rest is mostly defensive code (rare errors, malformed input) and a few unused helpers. Testing those adds little; the gate keeps the floor from slipping.
"Does high coverage mean no bugs?"
No. Coverage shows what ran. The functional cases show it did the right thing. Bug #27 was in code that was already covered: it ran, but it did the wrong thing in a situation no case described yet.
"Why is common lowest?"
It holds shared helpers: date ranges, error mapping, retries. Many branches handle errors that the features never trigger.
"Where is the gate configured?"
pom.xml, the jacoco-maven-plugin check execution, using the two properties on lines 27–28.
