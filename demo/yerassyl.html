  2. Point at the labels on a few rows. Each issue has three kinds of label. A kind: bug, enhancement, testing, or documentation. The modules it touches, like module:requests. And exactly one status: planned, ready, in progress, in review, blocked, or closed.

If the grader asks

"Why GitHub Issues?"
It sits next to the code, so commits, issues, and reviews link to each other, and the whole team and the graders can see it.
"Who decides the status?"
Whoever does the work moves it to in progress and in review. The team discusses each finished issue, and Jai closes it.
"How do you know a fix worked?"
Every fix comes with a test, usually a step in the test case that found it. The run report then shows the case as Passed.
"Why was #27 blocked rather than just fixed?"
Both fixes changed behaviour that users see, and the design gave no rule. So it waited for a decision, which is recorded in the issue.
