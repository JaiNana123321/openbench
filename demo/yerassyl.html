2. A bug found by a test case: #18 25:00–26:15

The bug, in one line: you couldn't mark a room booking as Priority at all, because that part of the app hadn't been built.

The fix, in one line: we built it: a Priority checkbox on room lines, the server call behind it, and a refusal for GPU lines.

  1. Tab 2, #18 "TC-DRF-04 drf-line-options: a Draft line cannot be marked Priority". Labels bug, module:requests, web. Body fields: Case, Build, Step, Expected, Observed, Evidence, Notes.
  2. The rule. A Manager can mark a room booking as Priority. It costs twice as much, and in return it can take the room from an ordinary booking. Compute, like GPUs, can't be Priority. You saw this in Jai's demo.
  3. What went wrong. Test case TC-DRF-04 checks that rule from both sides: a room line can be marked Priority, and a GPU line is refused. When we automated it on 7 November, the test failed with "404 Not Found". The double price and the database field were already there, but nothing let a user mark a line Priority. There was no checkbox and no server call.
  4. How we recorded it. We switched off just that one test and gave the reason, so the run report showed the case as only partly passing instead of hiding the failure. Then we filed this issue. It names the test case, the build, the step, what we expected, and what we actually saw, with the error message as evidence. Anyone can reproduce it from the issue alone.
  5. The fix. We added the checkbox on room lines and the server call behind it. Ticking it doubles the Quote, 30 credits to 60. GPU lines get no checkbox, and if anyone tries through the server, it refuses with PRIORITY_NOT_OFFERED. We switched the test back on, and it passes.
  6. Scroll to the timeline. status: ready (7 Nov) → in progress (12 Nov) → in review (15 Nov) → closed (17 Nov). Ready when filed, in progress while we built it, in review once it passed, and closed after the team discussed it. The Priority booking Jai used to bump oscar is this fix.

3. One bug through its whole life: #27 26:15–28:00

The bug, in one line: if a Request was bumped and then withdrawn, its GPUs stayed reserved for nobody, and the 60 credits paid for them were never refunded.

The fix, in one line: withdrawing is now refused until the Manager releases the GPUs, which refunds them and frees them for others.

  1. Tab 3, #27 "Withdrawing a Waiting Request after a Bump leaves its Allocated lines charged and holding capacity". Labels bug, module:allocation, module:requests.
  2. The setup, which you saw live. Oscar booked a room and 4 GPUs, and paid for both. Then alice took the room with a Priority booking. Oscar got the room's money back, and the Request went back to Waiting for a room. The GPUs stayed booked and paid for. All of that is correct.
  3. What went wrong. Before the fix, if Oscar then withdrew the Request, the screen said the GPU line was canceled. But the system never actually let go of the GPUs. The 4 GPUs stayed blocked for nobody, Oscar's 60 credits were never refunded, and nobody waiting for GPUs was offered them.
  4. Why it happened. Withdrawing was written for a Request that is Waiting, and a Waiting Request normally holds nothing for certain. So withdrawing only cleared tentative holds. A Bump is the one way a Waiting Request can still own a confirmed booking, and the code didn't handle that case.
  5. How we found it. Not by a test. We found it by reading the code when the Bump feature was merged. That's why the issue lists the three steps to reproduce it by hand, and says no test covered it yet.
  6. Point at "Decision needed". The design didn't say what should happen here, so we didn't guess. The issue offered two choices: refuse the withdrawal until the GPUs are released, or release them automatically with a refund. It stayed blocked until the team decided.
  7. The fix. We chose to refuse. Withdrawing now says "Release its allocated lines first". The Manager releases the GPU line, which refunds it under the normal refund rules and offers the GPUs to whoever is waiting. Then the withdrawal goes through. It's the smallest change, and Edit already refuses in exactly this situation, so the two now behave the same way.
  8. How we know it's fixed. We wrote a test that follows the same three steps. Before the fix, it failed: the withdrawal went through. Now the withdrawal is refused and nothing changes. After the GPUs are released, the withdrawal works. Jai showed that refusal live.

If the grader asks

"Why GitHub Issues?"
It sits next to the code, so commits, issues, and reviews link to each other, and the whole team and the graders can see it.
"Who decides the status?"
Whoever does the work moves it to in progress and in review. The team discusses each finished issue, and Jai closes it.
"How do you know a fix worked?"
Every fix comes with a test, usually a step in the test case that found it. The run report then shows the case as Passed.
"Why was #27 blocked rather than just fixed?"
Both fixes changed behaviour that users see, and the design gave no rule. So it waited for a decision, which is recorded in the issue.
